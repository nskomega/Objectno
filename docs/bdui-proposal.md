# Предложение: ограниченный BDUI / SDUI
Дата: 31.10.2026. Статус: исследование идеи Михаила, не утверждённая архитектура и не реализованный движок.

## Идея
Go-сервер описывает структуру отдельных экранов и данные, Flutter отображает разрешённые компоненты дизайн-системы. Можно позднее выделить библиотеку и Go-пакет в отдельный open-source проект, если подтвердится повторное использование.

## Границы
Go не рисует Flutter-виджеты: он отдаёт декларативный контракт, например JSON. Flutter содержит реестр типов, отображение, состояние формы и обработчики разрешённых действий. Сервер выбирает семантический вариант primary/secondary, а не произвольные HEX, шрифты и код. Тема, системное масштабирование, доступность и платформенное поведение сохраняются на клиенте.
Камера, видеозапись, авторизация, хранилище и геометрический редактор остаются обычными клиентскими возможностями. Сервер может запрашивать разрешённое действие, клиент проверяет его и выполняет соответствующий сценарий. Серверный манифест не даёт разрешений на данные и операции сам по себе.

## Первый эксперимент — предложение
Одна форма уточнения ремонта, 5 типов: text, textField, choice, card, button. Стабильные id узлов и полей, простая композиция без произвольного layout-языка. Два действия: submitForm, openKnownRoute. Go отдаёт один документ; Flutter показывает его в обеих темах и с увеличенным текстом. Сначала сравнить объём и удобство с обычной Flutter-формой.
Не включать в первый эксперимент скрипты, произвольные выражения, конструктор в браузере, универсальные анимации, все типы Flutter-виджетов и отдельный DSL.

## Контракт
- schemaVersion отдельно от версии приложения/сервера; documentRevision отдельно для обновлений конкретной формы.
- Клиент передаёт поддерживаемые capabilities/версии, сервер не отправляет неподдерживаемые обязательные компоненты.
- JSON Schema для формы документа и типизированные модели, проверка обязательных полей, ограничений размера/глубины/числа узлов.
- Неизвестный обязательный тип или несовместимая схема → понятный локальный fallback; не пропускать молча поля согласия, обязательные поля и критичные действия.
- Локальная базовая форма/последняя валидная совместимая схема для офлайн-сценария; сохранность черновика при обновлении документа.
- Допустимые действия, переходы и домены определяет клиент. Никакого выполнения кода из ответа сервера. Секреты и API-ключи не передаются в UI-манифесте.
- Проверка значений и авторизация повторяются на сервере; клиентская валидация — только помощь пользователю.

## Стоимость решения
Потребуются парсер, renderer, жизненный цикл состояния, совместимость схем, диагностика ошибок, контрактные и widget-тесты. Новый тип компонента всё равно требует обновления приложения. Изменение серверной схемы не отменяет тестирование и требования магазинов.
Цель — законченный продукт для портфолио; движок не должен откладывать его бесконечно. Отдельный репозиторий и лицензия обсуждаются после одного работающего сценария и оценки, действительно ли решение переиспользуется.

## Альтернативы для изучения
- Обычные Flutter-компоненты и API только данных: минимальный объём инфраструктуры.
- rfw (Remote Flutter Widgets) из экосистемы Flutter: проверить API, ограничения, поддержку и пригодность к JSON/Go-контракту перед выбором; не считать автоматической заменой нашего протокола.
- Shopify remote-dom как пример разделения удалённого описания и host-компонентов, не готовая Go/Flutter-библиотека.
