# Дизайн-система: обязательный процесс перед интерфейсом
Статус: правила и состав будущей системы, не завершённый визуальный дизайн приложения. Дата: 31.10.2026.

## Документы и границы ответственности
- Этот файл: принципы, процесс и требования к интерфейсу.
- `../design.md`: каталог UI kit, токены, состояния и правила компонентов.
- `decisions.md`: выбор и изменение визуальных решений с причинами.
- `../STATUS.md`: готовность дизайна и следующий шаг.
UI kit здесь означает набор интерфейсных компонентов, а не Apple UIKit. Пока Flutter-тема и Figma-библиотека не созданы, Markdown считается спецификацией, а не реализованным комплектом.

## Порядок
1. Описать назначение продукта, аудиторию, основные сценарии и ограничения.
2. Выбрать визуальное направление и платформенную основу. Для «Объектно» предварительное предложение — Material 3 с адаптацией платформенных взаимодействий; окончательно выбрать при создании системы.
3. Зафиксировать токены и спецификацию компонентов.
4. Подготовить эталонные экраны и состояния, проверить читаемость, длинный русский текст и масштабирование шрифта.
5. Реализовать тему и компоненты Flutter, затем продуктовые экраны. При изменении правил обновлять спецификацию и реализацию вместе.

## Обязательное содержание системы проекта
- Семантические цвета: фон, поверхность, основной текст, вторичный текст, действие, ошибка, успех, предупреждение, границы; темы и контраст проверяются на реальных сочетаниях.
- Типографика: гарнитура с кириллицей и допустимой лицензией, роли текста, размер/высота строки/вес, поведение при увеличении шрифта.
- Пространственная шкала: отступы, промежутки, радиусы, размеры иконок, ограничения ширины, safe area и клавиатура.
- Компоненты: кнопки, поля, карточка замечания, статус, фильтры, фото, диалог, уведомление, навигация. Для каждого: назначение, варианты, состояния, примеры использования и имя Flutter-компонента.
- Состояния экранов: пусто, загрузка, данные, ошибка, сохранение, недоступное разрешение, неподдерживаемый/отсутствующий файл. Состояния добавлять там, где они реально возможны.
- Доступность: подписи элементов и фото-кнопок, порядок фокуса, цвет не единственный носитель статуса, области нажатия, увеличение текста.
- Поведение: создание/редактирование/удаление, подтверждения и отмена, сохранение, переход назад, длинные тексты.
- Эталоны: список объектов, список замечаний, создание/редактирование замечания; необходимые варианты состояния.

## Контракт для ИИ
Перед изменением UI читать AGENTS.md, спецификацию дизайн-системы и существующие компоненты. Не вводить новые цвета, размеры и варианты компонентов без необходимости. Использовать семантические токены и ThemeData/ColorScheme/TextTheme; расширения темы — для отсутствующих продуктовых токенов. Не оборачивать каждый стандартный виджет без причины. Нестандартное решение описывать с причиной, затем обновлять спецификацию. Не копировать React/CSS-код из Figma в Flutter как готовую реализацию.

## Согласованность
Токены в коде — исполняемое представление системы. Markdown описывает назначение, правила и состояния. Figma при использовании должна отражать те же решения; при расхождении сначала выяснить источник изменения. После UI-изменения проверить соответствующие состояния на устройстве/эмуляторе и визуально сравнить с эталоном. Тесты добавлять на существенные сценарии и регрессии.
