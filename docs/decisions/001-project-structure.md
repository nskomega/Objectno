# ADR-001: структура приложения
Дата: 31.10.2026. Статус: принята как начальная структура будущего приложения по предложению Михаила. Структура применяется внутри Objectno; личные материалы вынесены в соседнюю папку Работа.

```text
lib/
  app/                     # запуск, конфигурация приложения и навигация
  design_system/
    tokens/                # семантические значения и шкалы
    theme/                 # ThemeData, ColorScheme, TextTheme, расширения
    components/            # переиспользуемые компоненты без бизнес-логики
  features/
    <feature>/             # экраны, состояние и данные конкретной возможности

docs/
  design-system.md          # принципы и правила
  decisions.md              # краткий индекс решений
  decisions/               # отдельные ADR с причинами и последствиями
STATUS.md
design.md                  # каталог UI kit и связи с кодом/макетами
```

## Причины
Разделить общие визуальные правила и продуктовые сценарии. Независимые архитектурные решения можно читать отдельно, не загружая весь журнал.

## Границы
- design_system не импортирует features; общие компоненты не знают о репозиториях данных или бизнес-процессах.
- Сущностные карточки (например IssueCard) первоначально живут в своей feature, если не доказана необходимость общего использования.
- tokens задают семантику; theme связывает её со стандартными Flutter-компонентами. Не поддерживать два независимых набора значений.
- Подпапки data/presentation и дополнительные слои вводить по потребности; не создавать пустые слои на будущее.
- В docs/decisions.md хранить индекс и краткие решения; подробные ADR — в docs/decisions/. Не дублировать полное описание.
- design.md — спецификация и каталог, Flutter-код — реализация. При расхождении обновить обе стороны осознанно.

## Последствия
Структура не выбирает пакет состояния, базу или навигационный пакет. Они определяются отдельными решениями после брифа.
