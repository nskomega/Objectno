# Версии и релизы

## Текущий этап
Текущая версия разработки хранится в VERSION. Это обозначение рабочего состояния, не выпущенный релиз. Теги и GitHub Releases пока не созданы. Уточнение Михаила: каждое завершённое логическое изменение получает отдельный коммит, следующую версию dev.N и запись CHANGELOG. Команды просмотра, промежуточные правки и незавершённые изменения не выдавать за готовую версию.

## Нумерация
Используем MAJOR.MINOR.PATCH с предрелизными суффиксами по SemVer. До 1.0 API нестабилен; несовместимые изменения всё равно явно описывать. Для приложения отдельно следить за совместимостью сохранённых данных и экспортируемых форматов.
- 0.1.0-dev.N — очередное завершённое изменение разработки; N увеличивается с каждым таким коммитом.
- 0.1.0-alpha.1 / beta.1 — проверяемые предрелизы соответствующей готовности.
- 0.1.0 — первый небольшой законченный выпуск; не создавать до готовности.
- PATCH — совместимые исправления; MINOR — новая функциональность. После 1.0 несовместимые изменения публичного контракта повышают MAJOR.

После создания Flutter-проекта version в pubspec.yaml согласовывать с VERSION. Номер сборки для магазина вести отдельно и увеличивать по правилам платформы; суффиксы разработки не переносить в магазин без проверки его требований. Flutter-проект создан; VERSION и поле version в pubspec.yaml синхронизировать.

## Рабочий процесс
1. После завершённого логического изменения обновлять VERSION и pubspec.yaml (dev.N и номер сборки), описывать изменение в CHANGELOG и делать отдельный содержательный коммит: feat:, fix:, docs:, refactor:, test:, chore:.
2. Значимые завершённые изменения добавлять в Unreleased: добавлено, изменено, исправлено, удалено; пустые разделы не нужны.
3. Перед релизом выбрать номер, обновить VERSION и pubspec.yaml при наличии, перенести Unreleased в раздел с номером и фактической датой.
4. Выполнить проверки для изменения: форматирование, анализ, тесты существенных сценариев и сборки целевых платформ. Не записывать проверки как пройденные без запуска.
5. Создать release commit и аннотированный тег vX.Y.Z, опубликовать GitHub Release с изменениями, проверками, известными ограничениями и подходящими сборками.
6. Для магазинного выпуска дополнительно подготовить карточки и материалы, проверить разрешения/данные и пройти review.

Один опубликованный тег соответствует неизменяемому содержимому: исправление — новый коммит и версия, без перезаписи релизных тегов. Публикация кода и выпуск приложения в магазине — разные события; отмечать их отдельно.

## Если появится Go-сервер
На старте использовать тот же репозиторий, каталог server/; приложение остаётся в корне. После появления независимого цикла выпуска ввести server/VERSION, server/CHANGELOG.md и теги server/vX.Y.Z. API совместимость документировать отдельно от номера приложения; OpenAPI и схема ошибок входят в контракт. Изменение схемы хранения требует миграции и плана отката.

## Git Flow — принято 11.11.2026

- `main` хранит стабильную историю выпусков; `develop` — базовая ветка интеграции. Существующую историю не переписывать.
- До изменения файлов создавать `feature/<сценарий>` от `develop`. Логические этапы по-прежнему получают отдельные коммиты, dev.N и номер сборки.
- Отправлять feature-ветку на GitHub, проверять SHA и открывать pull request в `develop` с фактическими результатами проверок. При заблокированных проверках оставлять draft PR и явно указывать причину.
- Для подготовки выпуска использовать `release/*` от `develop`, затем PR в `main` и обратный перенос исправлений в `develop`. Создание ветки не означает готовности релиза.
- Срочные исправления выпусков делать в `hotfix/*` от `main`, затем переносить через PR в `main` и `develop`.
- Без отдельного поручения не сливать PR автоматически и не отправлять рабочие коммиты прямо в `main` или `develop`.

Источник SemVer: https://semver.org/lang/ru/

Историю существующих коммитов не переписывать ради имитации постепенной разработки. Новые изменения фиксировать по мере готовности. GitHub remote: https://github.com/nskomega/Objectno.git. После завершённого этапа отправлять коммит в origin и проверять совпадение SHA локальной и удалённой ветки; локальный коммит сам по себе не означает push.
