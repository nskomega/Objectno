# Версии и релизы

## Текущий этап
Версия разработки: 0.1.0-dev.1 в VERSION. Это обозначение рабочего состояния, не выпущенный релиз. Теги и GitHub Releases пока не созданы. Версию не увеличивать после каждого коммита: историю изменений хранит Git.

## Нумерация
Используем MAJOR.MINOR.PATCH с предрелизными суффиксами по SemVer. До 1.0 API нестабилен; несовместимые изменения всё равно явно описывать. Для приложения отдельно следить за совместимостью сохранённых данных и экспортируемых форматов.
- 0.1.0-dev.N — этапы разработки при необходимости различать сборки.
- 0.1.0-alpha.1 / beta.1 — проверяемые предрелизы соответствующей готовности.
- 0.1.0 — первый небольшой законченный выпуск; не создавать до готовности.
- PATCH — совместимые исправления; MINOR — новая функциональность. После 1.0 несовместимые изменения публичного контракта повышают MAJOR.

После создания Flutter-проекта version в pubspec.yaml согласовывать с VERSION. Номер сборки для магазина вести отдельно и увеличивать по правилам платформы; суффиксы разработки не переносить в магазин без проверки его требований. Сейчас pubspec.yaml отсутствует.

## Рабочий процесс
1. Делать небольшие содержательные коммиты: feat:, fix:, docs:, refactor:, test:, chore:.
2. Значимые завершённые изменения добавлять в Unreleased: добавлено, изменено, исправлено, удалено; пустые разделы не нужны.
3. Перед релизом выбрать номер, обновить VERSION и pubspec.yaml при наличии, перенести Unreleased в раздел с номером и фактической датой.
4. Выполнить проверки для изменения: форматирование, анализ, тесты существенных сценариев и сборки целевых платформ. Не записывать проверки как пройденные без запуска.
5. Создать release commit и аннотированный тег vX.Y.Z, опубликовать GitHub Release с изменениями, проверками, известными ограничениями и подходящими сборками.
6. Для магазинного выпуска дополнительно подготовить карточки и материалы, проверить разрешения/данные и пройти review.

Один опубликованный тег соответствует неизменяемому содержимому: исправление — новый коммит и версия, без перезаписи релизных тегов. Публикация кода и выпуск приложения в магазине — разные события; отмечать их отдельно.

## Если появится Go-сервер
На старте использовать тот же репозиторий, каталог server/; приложение остаётся в корне. После появления независимого цикла выпуска ввести server/VERSION, server/CHANGELOG.md и теги server/vX.Y.Z. API совместимость документировать отдельно от номера приложения; OpenAPI и схема ошибок входят в контракт. Изменение схемы хранения требует миграции и плана отката.
